## 1. 트러블슈팅

### 1.1 에러 없이 알림이 멈추는 문제

**문제** — 운영 중 특정 시점부터 발송이 중단되었다. 잠자기에서 깨어난 뒤 밀린 알림 3건을 처리하고 조용히 끊겼는데, 예외 로그가 없어 원인을 찾기 어려웠다.

**원인** — 발송 작업이 자신의 다음 작업을 **같은 job id**로 예약하는 체인 구조였다. 밀린 알림을 연속 처리할 때는 "지금 즉시 실행"으로 예약되는데, 그 등록이 현재 작업이 아직 반환되기 전에 일어난다. APScheduler 입장에서는 "같은 id의 작업이 이미 실행 중인데 또 실행하라는 요청"으로 보여, 작업이 너무 오래 걸려 밀린 상황으로 판단하고 신규 작업을 폐기했다 (`max_instances` 기본값 1).

결정적으로 이것은 **예외가 아니라 경고 로그**였다. 당시 체인 유지를 위해 넣어둔 예외 기반 재시도 로직으로는 잡히지 않았고, `date` 트리거는 한 번 폐기되면 재실행이 없어 체인이 그대로 죽었다.

**해결** — 해당 동작만 격리해 재현(8회 실행을 의도한 체인이 1회에서 끊김)하여 원인을 특정했다. 그 뒤 두 방향으로 대응했다.

- **원인 제거** — 지나간 알림을 발송 대상에서 제외하도록 정책을 바꿨다. 연속 즉시 예약이 사라지므로 경쟁 조건 자체가 발생하지 않는다.
- **안전망** — 예약이 유실된 시트를 주기적으로 찾아 복구하는 감시 작업을 추가했다(`WATCHDOG_INTERVAL_MINUTES`, 기본 15분). 조용히 사라지는 경우는 예외로 감지할 수 없으므로, 원인에 무관하게 상태를 점검하는 장치가 필요했다.

감시 작업에는 `_in_flight` 집합이 함께 필요했다. `date` 작업은 실행이 시작되는 순간 저장소에서 제거되므로, 발송 중인 시트는 "예약이 없는" 상태로 보인다. 이를 고장으로 오해해 재예약하면 같은 알림이 두 번 나간다.

### 1.2 서버 재시작 시 중복 발송

**문제** — 재시작 시 동일한 알림이 반복 발송되었다. 실제로 6분 사이 6회 중복이 발생했다.

**원인** — 발송 이력이 스케줄러 메모리에만 존재해 프로세스 종료와 함께 사라졌다. 기동 시 "지금 이후 가장 가까운 행"을 다시 선택하는데, 알림 예정 시각(행 시각 − `NOTICE_LEAD_MINUTES`)과 행 시각 사이 구간에서 재시작하면 **방금 보낸 행이 아직 미래**이므로 또 선택된다. 그리고 예정 시각은 이미 지났으므로 과거로 예약하지 않기 위한 보정에 의해 즉시 발송된다.

개발 중 코드 리로드로 드러났지만, 재부팅·크래시 복구·배포에서도 동일하게 발생하는 문제였다.

**해결** — `sheet_registrations.last_sent_row_at`에 발송을 끝낸 행 시각을 기록하고, 같은 행이 다시 선택되면 발송을 건너뛴다. 프로세스 생명주기와 무관해야 하므로 메모리가 아니라 DB에 둔다.

발송 테스트 엔드포인트는 이 기록을 남기지 않는다. 수동 확인이 예약된 정규 발송을 조용히 취소해서는 안 되기 때문이다.

### 1.3 타임존

**문제** — 전 구간이 naive `datetime.now()`였다. 개발 환경(KST)에서는 정상이지만, 서버 시간대가 UTC인 환경(컨테이너·클라우드 기본값)에 배포하면 9시간 어긋난 시각에 발송된다.

**원인** — 시트에 적힌 `09:00`은 명백히 한국 시각인데, 그 가정이 코드 어디에도 표현되지 않았다. OS 시간대에 암묵적으로 의존하고 있었다.

**해결** — `TIMEZONE` 설정을 두고 전 구간을 aware datetime으로 전환했다. 스케줄러에도 타임존을 명시했다. 다만 행 시각 비교는 의도적으로 벽시계 기준(`.time()`)으로 남겼다 — 시트에 적힌 `09:00`에는 타임존 개념이 없기 때문이다.

검증은 프로세스 시간대를 UTC로 강제한 상태에서 수행했다. naive `now()`가 UTC를 가리키는 상황에서도 예약이 KST 기준으로 잡히는지 확인했다.

### 1.4 수신자 명단이 서로에게 노출됨

**문제** — 수신자 전원을 `To` 헤더에 넣어, 받는 사람마다 다른 팀원의 주소를 전부 보게 되었다.

**원인** — SMTP에서 실제 배달 대상을 결정하는 것은 헤더가 아니라 `sendmail()`에 넘기는 봉투(envelope)다. 헤더는 표시용에 불과한데, 두 가지를 같은 것으로 다루고 있었다.

**해결** — `To` 헤더에는 발신자 자신만 넣고, 수신자는 봉투로만 전달한다. 배달은 그대로 전원에게 가면서 명단은 노출되지 않는다. `Bcc` 헤더는 넣지 않았다 — 서버 구현에 따라 명단이 그대로 전달될 수 있고, 봉투에만 주소를 두면 숨은참조는 이미 성립한다.

### 1.5 외래키 제약이 동작하지 않음

**문제** — 팀 구조를 도입하면서 `ON DELETE CASCADE`를 선언했는데, 팀을 삭제해도 멤버와 연결이 그대로 남았다.

**원인** — SQLite는 외래키 제약을 **선언은 받아들이지만 기본적으로 검사하지 않는다**. 하위 호환을 위한 기본값이며, `PRAGMA foreign_keys`는 연결(connection)마다 적용되는 설정이다.

**해결** — 커넥션 풀이 새 연결을 만들 때마다 `PRAGMA foreign_keys=ON`을 실행하도록 이벤트 리스너를 등록했다. 기동 시 한 번만 실행하면 그 연결에만 적용되어, 요청마다 동작이 달라지는 상태가 된다.

### 1.6 잠자기 후 밀린 알림을 어떻게 다룰 것인가

버그가 아니라 **정책 결정**이다. 호스트가 11시간 잠든 뒤 깨어났을 때 선택지는 두 가지였다.

| | 동작 | 결과 |
|---|---|---|
| 따라잡기 | 밀린 알림 전부 발송 | 기상 시 최대 21통 |
| **건너뛰기** | 지나간 알림은 버리고 다음 것부터 | 기상 시 0~1통 |

**건너뛰기를 선택했다.** 02:00 근무 알림을 13:00에 받는 것은 정보로서 가치가 없고, 한꺼번에 쏟아지는 알림은 오히려 중요한 알림을 묻는다. 알림의 수단이 아니라 목적을 기준으로 판단했다.

유예는 `NOTICE_LEAD_MINUTES`를 재사용했다. 행 시각 기준 전후 같은 폭이며, "10분 먼저 보내는 것이 적절하다면 10분 늦은 것도 비슷하게 유효하다"는 판단이다. 설정값을 하나 더 늘리지 않는 쪽을 택했다.

## 2. 설계 결정

### 2.1 고정 주기 스캔 대신 체인 예약

전체 시트를 N시간마다 순회하는 방식에서, **각 시트의 다음 발송 시각에만 단발성 작업을 예약하고 발송 후 다음 작업을 잇는 방식**으로 바꿨다.

주된 이유는 **행 시각에 맞춘 정확한 발송**이다. 행이 9:00, 13:30처럼 제각각이고 그 10분 전에 보내야 하므로, 1시간 주기로 스캔하면 8:50이나 13:20에 맞출 수 없다. 맞추려면 1분 주기로 스캔해야 하고, 그러면 시트 읽기가 하루 1,400회 이상 발생한다. 체인 방식은 각 행의 정확한 시각에 한 번씩만 작업이 돈다.

API 호출량은 부차적인 이유이며 행이 얼마나 촘촘한지에 따라 결과가 갈린다. 스캔마다 시간 열을 한 번 읽고 일치하는 행이 있을 때만 데이터를 읽는 구조를 가정하고(첫 구현의 정확한 호출 수는 기록이 없어 추정), 체인은 알림 1회당 3회(예약 1회 + 발송 2회)로 계산했다.

| 시트 | 체인 | 1시간 주기 스캔 | 1분 주기 스캔 |
|---|---|---|---|
| 하루 22행 (현재 시트, 매시간) | 66회 | 46회 | 약 1,460회 |
| 하루 2행 | 6회 | 26회 | 약 1,440회 |

하루 행이 12개를 넘으면 체인이 1시간 주기 스캔보다 호출이 오히려 많다. 따라서 호출 수만 보면 체인이 항상 유리한 것은 아니고, **정확한 시각을 맞춰야 한다는 조건에서 1분 주기 스캔과 비교할 때** 유리하다.

대가가 있다. 각 단계가 다음 단계를 예약해야만 알림이 이어지므로, 한 번의 실패가 영구 중단으로 이어진다. 그래서 예약 단계는 어떤 예외도 밖으로 던지지 않고 재시도를 예약하며(`SCHEDULE_RETRY_MINUTES`), 그것으로도 잡히지 않는 경우를 감시 작업이 덮는다. 1.1은 바로 이 구조의 취약점이 드러난 사례다.

### 2.2 시트 레이아웃을 설정으로 분리

시트마다 시간이 적힌 열, 데이터 범위, 데이터가 시작되는 행, 시각 표기(`09시` / `9:00`)가 다르다. 이를 코드에 두면 시트가 추가될 때마다 코드를 고쳐야 한다.

등록 시 이 값들을 받아 저장하는 구조로 분리해, **코드 변경 없이 새로운 형식의 시트를 추가**할 수 있게 했다. 대신 등록 단계에서 열 표기를 검증한다 — 잘못된 값이 저장되면 발송 시각이 되어서야 오류가 드러나기 때문이다.

### 2.3 팀과 시트를 중간 테이블로 연결

한쪽에 외래키를 두면 "팀 1 : 시트 1"이 되어, 같은 팀이 두 개의 시트를 쓰려면 팀을 두 개 만들고 멤버를 중복 등록해야 한다. 공용 시트를 전제로 하면 중간 테이블이 필요하다.

그 결과 한 사람이 같은 시트를 공유하는 두 팀에 속할 수 있고, 조인 결과에 같은 이메일이 두 번 나타난다. 수신자 조회에서 중복을 제거해 한 통만 가도록 했다.

팀을 삭제할 때 멤버와 연결은 함께 지우되 **시트는 남긴다**. 다른 팀이 공유 중일 수 있기 때문이다.

### 2.4 서비스 레이어는 예외 대신 값을 반환한다

서비스 함수는 `None`, `False`, 또는 `"no_team"` 같은 결과 코드를 반환하고, HTTP 예외는 라우터에서 생성한다.

서비스의 호출자가 **라우터와 스케줄러 둘**이기 때문이다. 스케줄러는 HTTP와 무관하므로 `HTTPException`을 받아도 할 수 있는 일이 없다. 서비스가 HTTP 예외를 던지면 웹 요청에서만 의미가 있는 코드가 된다.

### 2.5 서비스 계정과 읽기 전용 권한

OAuth 사용자 인증은 사람의 로그인과 동의가 필요해, 무인으로 돌아야 하는 스케줄러에 맞지 않는다. 서비스 계정은 그 자체가 독립된 계정이므로 사람의 개입 없이 인증된다. 대상 시트를 서비스 계정 주소와 공유하는 것이 조건이다.

권한 범위는 `spreadsheets.readonly`로 제한했다. 이 앱은 읽기만 하므로, 키가 유출되더라도 토큰에 쓰기 권한이 없어 시트를 수정하거나 삭제할 수 없다.

### 2.6 테스트는 네트워크를 차단한 상태에서 돈다

구글 API와 SMTP 소켓을 기본적으로 막는 픽스처를 두어, 스텁을 설치하지 않은 테스트가 외부로 나가려 하면 그 자리에서 실패하게 했다. 실수로 실제 메일이 발송되는 일을 구조적으로 막는다. DB도 임시 파일을 사용해 운영 DB를 건드리지 않는다.

외부 연동을 `*_client.py`로 격리해둔 덕에, 함수 하나를 대체하면 전체 로직을 검증할 수 있다.

## 3. 알려진 한계

의도적으로 미뤄둔 것들이다. 현재 사용 규모(시트 1개, 수신자 2명)에서는 비용이 효용을 넘는다고 판단했다.

| 한계 | 영향 | 넘어가려면 |
|---|---|---|
| **호스트 잠자기에 의존** | 스케줄러가 앱 프로세스 안에서 돌아, 호스트가 잠들면 멈춘다. 자는 동안의 알림은 건너뛴다 | `caffeinate`로 실행하거나, 상시 가동되는 별도 호스트로 이전 |
| **API 인증 없음** | Tailscale 내부 사용을 전제했다. 같은 네트워크의 누구나 시트·수신자를 조작할 수 있다 | 외부 노출 전 토큰 검증 추가. 바인딩 주소도 `0.0.0.0`에서 좁혀야 한다 |
| **문서의 첫 탭만 읽음** | range에 탭 이름을 붙이지 않아 맨 앞 탭만 대상이 된다. 월별로 탭을 나눈 문서는 등록할 수 없다 | 등록 정보에 탭 이름을 추가하고 range에 접두. URL의 `gid`로 자동 선택 가능 |
| **같은 시각 행이 여럿이면 첫 행만** | 동일 시각에 복수 항목이 배정된 표에서 나머지가 누락된다 | 매칭되는 모든 행을 수집해 본문에 합치기 |
| **발송 1회당 구글 API 3회** | 예약 1회 + 발송 2회. 시트 수에 비례해 쿼터를 소비한다 | `batchGet`으로 묶거나, 시각 열 파싱 결과를 캐싱 |
| **일부 수신자의 발송 실패를 감지하지 못함** | `sendmail()`은 일부 수신자만 거부돼도 예외 없이 거부 목록을 반환값으로 돌려주는데, 코드가 그 값을 확인하지 않는다. 전원이 거부될 때만 예외로 잡히며, 일부가 거부돼도 로그는 "발송 완료 (수신자 N명)"으로 남는다. 서버가 접수한 뒤의 배달 실패(반송)는 어떤 방식으로도 SMTP로는 알 수 없다 | 반환값을 확인해 거부된 수신자를 경고로 남김. 수신자별로 개별 발송하면 결과를 수신자 단위로 볼 수 있고, 일시적 오류만 같은 작업 안에서 짧게 재시도하고 영구 오류는 로그로 남기는 방식을 검토했다. 별도 job으로 재시도하면 시트의 체인 job과 id가 겹쳐 체인을 덮어쓸 수 있고, 재시작 시 재시도가 사라지는 점을 감수해야 한다 |
| **받는사람 화면에 발신자 주소가 보임** | `To` 헤더에 발신자 본인만 넣은 것은 수신자끼리 주소가 노출되는 것과 전체 답장이 전원에게 가는 것을 막기 위한 선택이다. 대가로 받는 사람은 자기 주소가 아니라 발신자 주소를 받는사람으로 보게 된다. 배달에는 영향이 없다 | 수신자마다 개별 발송하며 `To` 헤더에 그 사람의 주소를 넣는다. 전송 횟수가 수신자 수만큼 늘어나고, 수신자 수백 명 이상이면 현재 방식이 더 효율적이다 |
| **기동 비용이 시트 수에 비례** | 기동 시 시트마다 1회씩 호출한다. 수천 개를 넘으면 쿼터 한도에 막혀 기동 자체가 지연된다 | 다음 발송 시각을 컬럼으로 저장하고, 1분 주기로 "임박한 것만" 조회하는 방식으로 전환. 재시작 복구도 함께 해결된다 |

마지막 항목이 구조적으로 가장 큰 제약이다. 현재 설계는 "모든 시트를 미리 예약"하는 `O(전체)` 구조이며, 규모가 커지면 `O(임박한 것)`으로 바꿔야 한다. 전환 지점은 기동 시간이 체감될 때(수백 개 수준)로 본다.
